## 一、`render.ts`：渲染层

### 1.1 模块定位与依赖方向

> 命盘渲染层 —— 把排盘内核输出的结构化数据，渲染成给模型读的文本片段。
>
> 拆自 purple-star.ts。只依赖 `@/` 内核，不依赖本目录的其他模块 —— 唯一例外是
> `import type { CaliberBasis } from "../birth/birth-info-defs"`（候选 6 的 basis 签名，
> 类型 import 运行时被完全擦除，不形成运行时边）与 `./chart-cache`（晚子时对照盘
> 走排盘缓存，birth-info → render（fmtDate）的依赖方向同样不破）。
> 故本文件仍处依赖图底层（args / render 并列底层）。
>
> ⚠️ 本文件由引导层在 `registerHooks` **之后**动态加载，故这里可以放心用
>    静态 import 引内核与 `@/` 别名。但**不要**反过来让 purple-star.ts 静态引本文件。

### 1.2 `FOCUS_ALIASES`：四种写法都收进来

> `--focus` 的宫名别名表：四种写法 → 项目口径宫名。
>
> 宫名口径已改为项目本位（倪师《天纪》体系，见 `constants.ts` 的 `IZTRO_TO_PROJECT_PALACE`），
> 但用户嘴里说的、别的排盘软件里写的仍是老叫法。这里把四种写法都收进来，
> 免得模型照用户原话传参却聚焦失败：
> 项目全名（交友宫）· 口语简称（交友，去「宫」字）· iztro 旧口径（仆役）· 旧口径加宫（仆役宫）。
>
> 地支名（子/丑/…）不在此表，由匹配处单独比对。
> 整张表从 `IZTRO_TO_PROJECT_PALACE` 派生，故不会与内核映射表漂移。

### 1.3 `palaceAtBranch` 薄壳

> 命宫 / 身宫地支必定落在 `palaces` 内，这是排盘不变量；取不到即说明内核输出已损坏。
> 此处遵循项目一贯立场：宁可当场失败，也不要渲染出一张缺了命宫的盘。
>
> 实现已收敛至 `@/palace-relations` 的 `mustPalaceAtBranch`（候选 8）——
> 本函数是薄壳，保持既有调用方与导出名不变。

### 1.4 `mustPalace`：宫名口径漂移的代价

> 这里原先写的是 `find(p => p.name === "夫妻")`（iztro 旧口径）。宫名改为项目口径后
> 它会静默返回 undefined，而调用点紧接着就读 `.branch` —— 合盘会以 TypeError 崩掉，
> 报错还指不到真正的原因（「Cannot read properties of undefined」）。宫名是耦合点，
> 取不到就该当场说清是哪个名字、当前的十二宫叫什么。

### 1.5 `chartSignature`：**唯一实现**

> 命盘指纹：宫名 + 地支 + 全星曜集合，用于比对两盘是否完全一致。
>
> 本函数是**唯一实现** —— `test/lib/compare.ts` 经 `test/lib/loader.ts` 的 `loadRender()`
> 转出它，CLI 与测试共用同一份代码。（此前 test/ 侧另有一份逐行副本，两侧靠注释互相提醒
> 「必须同步」，却没有任何断言盯着；只在一侧加排序就会静默分叉。）
>
> 先按 `branch` 排序再拼接，使指纹与 `palaces` 的数组顺序无关（该顺序实测为
> 寅起的 `2,3,…,11,0,1`，不是 0-11）。

### 1.6 `lateZiSection`：晚子时两盘并列

> 23:00–23:59 出生时，子时横跨两日：「当日早子时」与「晚子时算次日」排出的是两张不同的盘。
> 故这里会**另排一张对照盘**并把两张盘的紫微位与命宫主星并列出来（`isLateZi` 时对照当日早子时
> `timeIndex: 0`，否则对照晚子时 `timeIndex: 12`）。对照盘与主盘走**同一个缓存层**
> （`./chart-cache`，键是出生信息哈希）——它是另一份 BirthInfo，故占另一个缓存条目，
> 但同样只排一次。
>
> 措辞锚在「校正后」而非「你给的钟表时间」：开 `--eot` 或西部城市时，落在 23:00–23:59 的
> 往往是校正后的真太阳时，钟表时间可能在别处（如喀什 02:30 校正后是前一日 23:37）。

`renderPalace`（借对宫的来源）：

> 主星为空时改写「借对宫 X 的 Y」—— `borrowedFromName` / `borrowedStars` 由内核算好，
> 这里不现算。

## 二、`chart-cache.ts`：排盘缓存层

### 2.1 为什么需要它

> 本 skill 是「一次调用、一次冷启动」的形态：助手每轮解读都要重跑
> `node scripts/purple-star.ts astrology …`，而排盘（`generateChart` → iztro + 本项目组装）
> 是端到端耗时的大头。同一份出生信息在一轮对话里往往被反复排（换专题参数、换视角、
> 追问某一宫都要重来一次），而**排盘对同一份 `BirthInfo` 是确定性的**——把它落盘，
> 第二次起就只剩「读文件 + 渲染」。

### 2.2 缓存什么、不缓存什么

> 缓存的是 `generateChart` 的返回值（`ZiweiChart`，纯数据）——`--palaces --json`
> 本就直接序列化它，JSON 往返结构上无损耗。**不缓存任何渲染文本**：渲染由一堆纯函数
> 从 chart 派生，几乎不花钱，却与专题参数（`--pattern` / `--topic` / …）强相关；
> 把文本缓存下来等于把整张参数面也塞进缓存键，代价高、收益低。

### 2.3 失效靠两个维度

> 1. **格式版本 `CACHE_VERSION`** —— 改 `generateChart` 的输出结构、改盘算法口径、
>    或升级 iztro 之后必须递增；递增即整批失效（重排一次的事）。
> 2. **农历年 `lunarYear`** —— `generateChart` 内部的 `currentAge` 是**虚岁**且以农历
>    正月初一为界（algorithm.ts），同一农历年内它恒定、跨年必变。故缓存只在本农历年内
>    有效：跨春节后首次调用自动重排，不会把去年的虚岁当成今年的。

### 2.4 正确性优先于命中率

> 读取、解析、结构校验、**出生信息回验**任何一步不通过，一律当未命中 → 重排 → 覆写。
> 出生信息回验是哈希碰撞的守卫：宁可重排一次，也不能把 A 的盘发给 B。
> 写盘失败（只读文件系统 / 磁盘满）静默跳过 —— 缓存是性能优化，不参与正确性，
> 不能因为缓存写不进去就让排盘失败。

### 2.5 `CACHE_VERSION`

> 缓存**格式**版本（不是排盘算法版本）。
>
> ⚠️ 改 `generateChart` 的输出结构（`ZiweiChart` 字段增删改）、改盘算法口径、或升级
> iztro 之后**必须递增**：旧文件里的 `chart` 可能已经与新内核不同形。
> 递增即整批失效，成本是每个生日重排一次 —— 远小于「拿错盘」。

### 2.6 `cacheRootDir`：为什么不写 skill 目录

> **为什么不放 skill 目录**：本仓整个可拷进 `~/.claude/skills/` 直接使用，缓存是
> **机器级**的派生数据（随时可重建）。写进包目录会让「拷走即干净」这条性质失效 ——
> 还得为它加 .gitignore、还得防它被误提交。落到系统临时目录则包内零写入。
> 附带好处：同一台机器上有多份拷贝时**共享同一份缓存**，不必各排一次。
>
> **为什么目录名带 uid**：POSIX 的 `/tmp` 是**多用户共享**目录，而缓存文件里装的是
> 生辰命盘数据 —— 既不该被别的用户读到，也不能让别人抢占了同名目录再让本进程写失败。
> 目录名带 uid + `writeEntry` 建目录时用 `0o700`，两道都必要（Windows 的
> `os.tmpdir()` 本就是 per-user 私有目录，那里只起冗余保护作用）。
>
> **为什么目录名带 `CACHE_VERSION`**：递增版本即换目录，天然与旧格式缓存隔离，
> 不必担心「旧文件混进新目录」。
>
> **代价（刻意的取舍）**：系统会清理临时目录，重启即冷排一次；临时目录空间也有限
> （本机 `/tmp` 是 10 MB tmpfs，按 ~9 KB/张约合千张），写满时 `writeEntry`
> 静默降级为现排。缓存只为提速，丢了只慢一次，不影响任何结果。
> 需要持久缓存就设 `ZIWEI_CACHE_DIR`（如 `~/.cache/purplestar-astrology`）。

`userTag`：

> 用户隔离标签：`u<uid>`（POSIX）或 `n<用户名>`（拿不到 uid 时，如 Windows）。
>
> 拿不到就退回共享标签 —— 此时 `/tmp` 里的目录可能被别人抢先创建，但写盘失败会被
> 静默降级为现排，不会排错盘。

### 2.7 `CacheEntry`：落盘的跨版本契约

> ⚠️ 这是**落盘的跨版本契约**：改键名 / 改语义就要把 `CACHE_VERSION` 递增，
> 否则旧文件会被当有效缓存读回来。

### 2.8 `canonicalBirth` 与 `cacheKeyOf`

> 出生信息的规范化序列化 —— **固定键序的短键**，与字段书写顺序无关。
>
> 为什么不用 `JSON.stringify(birth)`：对象键序取决于键的插入顺序，同一份出生信息
> 经不同路径构造出来可能序列化成不同字符串，缓存键就会飘。定序短键消除这一类，
> 且顺手把键名压短。

> 缓存键：出生信息的 sha256 十六进制串（即缓存文件名，不含扩展名）。
>
> sha256 而非短哈希：文件名长一点无所谓，而生日空间的键必须**绝不碰撞**——
> 碰撞的后果不是丢性能，是可能把一张盘发给另一个人（由 `readEntry` 的
> 出生信息回验兜底，但那是最后一道防线，不该指望它）。

### 2.9 `readEntry`：绝不抛错 + ⚠️ JSON 往返丢 `undefined`

> 本函数**绝不抛错**：无文件不是错误（首次排盘就是它），文件损坏（半截 JSON / 非法
> 语法）也不是 —— 它只是「缓存不可用」，由调用方重排覆写。故 `readFileSync` 与
> `JSON.parse` 两处失败都静默吞成 `null`。
>
> ⚠️ JSON 往返会丢掉值为 `undefined` 的可选键（`Star.mutagen` / `palace.decadalRange`
>    / `brightness` 等 stringify 时消失），这是**结构上**与内存态 `ZiweiChart` 兼容的
>    （可选键本就允许缺失），下游读的都是可选链。故缓存返回的对象缺这些键属正常，
>    测试对拍时双方都要先归一到 JSON 形态再比。

哈希碰撞守卫（行内）：

> // 哈希碰撞守卫：键指向的盘必须是这一份出生信息的盘。挡不住就把 A 的盘发给 B，
> // 比多排一次盘恶劣得多。

### 2.10 `writeEntry`：原子写 + 静默降级

> 原子写盘：先写同目录临时文件再 `rename`。
>
> `rename` 在同目录内是原子的 —— 两个进程同时排同一张盘时，后落地的那个 rename 只是
> 覆盖成同内容，读者永远不会看到截断的半截 JSON（`writeFileSync` 直写则可能）。
>
> ⚠️ 失败一律**静默降级**：写盘只为提速，命盘此刻已在调用方手上，此时再抛错就是
>    「缓存写不进去 → 排盘也失败」，与本层的承诺相反。故 catch 里连临时文件的清理
>    都再包一层 try —— 目录根本不可用时 `rmSync` 同样会抛（ENOTDIR / EACCES），
>    那一次抛错曾直接把整个调用顶穿。
>
> 建目录用 `0o700`：缓存文件里是生辰命盘数据，默认临时目录多用户可读不该对它生效。
> （目录已存在时 mode 不变 —— 此时能读到它的人当初就已拿到过读权限。）

### 2.11 `generateChartCached`：禁缓存的单点判定

> 排盘 + 缓存：本模块对外的**唯一**入口，替代裸调 `generateChart`。
>
> 禁缓存在此**单点**判定（参数 `--no-cache` 与环境变量 `ZIWEI_NO_CACHE` 都归一到这里）：
> selftest 与 `npm test` 走进程内排盘，必须强制直排 —— 否则内核改动后回归会命中改动前
> 写下的缓存文件而**假绿**，那比没有回归更坏。
>
> 缓存失败一律静默降级为「现排、不缓存」：命中与否不影响结果，只影响速度。

## 三、`host/dispatch.ts`：分发协议

### 3.1 唯一真相源 + ⚠️ 不写盘不 print 不 exit

> dispatch.ts —— argv → { code, out, err, outFile } 的分发协议（候选 1）。
>
> 唯一真相源：未知命令文案、--help 拦截位置、错误前缀、参数解析 → 执行次序。
> 此前这条链有 6 份独立实现（purple-star main / selftest call / corpus asserts /
> synastry asserts / cli-samples / cli.test），未知命令文案 5 种变体 —— 本模块收拢后，
> 各调用点退化为同一 seam 上的 adapter（写 stderr / 收进 Assertion / 渲染样例 / 断言）。
>
> ⚠️ 本模块**不写盘、不 print、不 exit**：副作用全部归宿主（purple-star 的 main），
> 进程内测试（selftest）与子进程真链路（guard 冒烟）因此消费同一 seam。
> `--out` 落盘也归宿主：dispatch 只把路径带出来（`outFile`），不碰文件系统。

### 3.2 `DispatchPorts`：两个 loader 都是惰性的

> 两个 loader 都是惰性的：help / 未知命令路径只触发 `loadHelp`（轻模块，不付出
> iztro 冷启动）；真正执行命令时才触发 `loadCore`（含启动自检）。

### 3.3 `--help` 拦截位置（接口承诺）

> `--help` / `-h` 出现在**任何位置**都打印 help，包括 `astrology --help`。这是刻意的：
> `--help` 不在参数声明表里，放它走到 parseArgs 只会得到一句「未知参数 --help」，
> 而用户此刻想要的显然是用法。判定提前到分发之前，parseArgs 因此永远见不到它 ——
> 判定顺序是本模块的接口承诺，由 selftest 的 runDispatchProbe 钉住。
>
> 未知命令与命令内部抛出的错误都返回 code=1（只带 err.message，不带栈），
> 打印与退出归宿主。

### 3.4 `formatError` 前缀真相源

> 命令失败文案的唯一前缀构造：`错误：<message>`（不带栈）。
>
> dispatch 的执行 catch 与宿主的副作用 catch（`--out` 落盘）共用 —— 前缀真相源一处，
> 否则「错误：」会在宿主里再抄一份。

### 3.5 旧命令迁移提示

> 旧命令并入提示：stars / oracle 已并入 `--source` 选域，classics 随四域合并改名
> knowledge —— 敲旧名给一条可直接照抄的迁移写法，而不是让用户自己从 help 里找。

## 四、`host/out.ts`：`--out` 落盘通道

> `--out` 的落盘通道 —— 把命令产出的文本写到用户指定文件。
>
> 写入点收敛在唯一函数：路径先过 `..` 段校验（穿越防护，子目录与绝对路径不受影响），
> 再整体写盘。末尾补的这一个换行与 `console.log` 的输出行为逐字一致 —— 两条通道
> 产物可 diff 对拍；落盘后正文不再占 stdout（进度提示由引导层走 stderr）。
