## 三、方法产出：如何给「零基准」的模块建立独立基准

这是本次测试最有价值的部分，也是 [docs/test/README.md](README.md) 那条教训的直接应用：

> **判断一个交叉验证有没有价值，先问：它和被测对象共享了多少计算路径。**

格局与合盘在数据集里**没有基准**（样本无 `patterns` 字段、样本是单人盘），而这两处的实现又
**无法用同源比对验证**——拿 `patterns.ts` 自己算的期望值去比对 `patterns.ts`，只是复读机。

本次改用**紫微斗数安星规律推导的确定性等价关系**。这类关系的正确性来自安星法本身，
与被测实现零共享路径：

| 等价关系                                                                 | 来源               |
| ------------------------------------------------------------------------ | ------------------ |
| 紫府同宫 ⟺ 紫微与天府同宫 ⟺ 紫微落在寅或申                               | 紫微/天府安星表    |
| 天府与天相恒相隔 4 宫                                                    | 十四主星排布恒等式 |
| 杀破狼 ⟺ 七杀/破军/贪狼三星齐入命宫三方四正                              | 格局定义           |
| 府相朝垣 ⟺ 天府与天相均在命宫三方四正且不同宫                            | 格局定义           |
| 十二宫相对命宫的偏移固定（命 兄 夫 子 财 疾 迁 友 官 田 福 父 = 0,−1,…） | 十二宫排列恒等式   |
| 格局识别结果与性别无关（性别只影响大限顺逆）                             | 安星法             |

> ⚠️ **这些关系的边界**：它们验证的是「识别逻辑与安星规律是否一致」，**不是**「格局的命理判词是否
> 正确」。判词取自古籍，属知识层，无外部可验证源 —— 和 04 号报告里 taibu 交叉验证的边界同构。

## 四、发现的问题

### 🟡 P1：宫名口径未文档化，「交友宫」查不到（会直接导致误用）

CLI 的十二宫用**「仆役」**，而紫微斗数日常更常说**「交友宫」**。SKILL.md 只写 `--focus <宫名>`，
举例恰好是「财帛」「官禄」这两个两家通用的名字，**从未列出过标准宫名**。

```bash
$ node scripts/purple-star.mjs analyze --date 1990-05-15 --time 09:30 --gender male --focus 交友
【聚焦失败】找不到宫位「交友」。可用：福德、田宅、官禄、仆役、迁移、疾厄、财帛、子女、夫妻、兄弟、命宫、父母
```

用户说「看看我的交友宫」时，模型很可能直接传 `--focus 交友` 而失败。
**失败提示本身是好的**（列出了全部可用宫名），属于可用性缺口而非逻辑缺陷。

同时实测到两条**未文档化的能力**：`--focus` 也接受**地支名**（`--focus 子` → 命宫），
以及 `--focus` 的匹配是 `p.name === focus || BRANCHES[p.branch] === focus`。

**建议**：SKILL.md 补一张十二宫标准名表，并注明可用地支。

### 🟡 P2：内核行数漂移

SKILL.md 称「**6613 行**自定义内核代码（`scripts/` 下 `.ts` 计，不含 `lunar-javascript.d.ts`）」，
实测 **6621 行**（`6648 − 27`），差 8 行。

`patterns.ts` 的「1190 行」则**准确**。说明只有总数这一处失准，属内核演化后未回填。

### 🟡 P3：`npm test` 耗时在 SKILL.md 与 test/README 中互相矛盾

两处**自相矛盾**，SKILL.md 的那个是陈旧值。（8.0 秒为无后台负载时的干净测量。）

### 🟢 P4：`selftest` 首行内容描述失准

### 🟢 P5：目录结构图缺 `test/`、`docs/`

SKILL.md 的目录结构图只列了 `SKILL.md / README.md / LICENSE / package.json /
package-lock.json / scripts/ / node_modules/`，但正文明确引导读者去跑 `npm test`
并阅读 `test/README.md` —— 图与正文对不上。根目录另有未列出的 `tsconfig.json`
与 `docs/`。

> 注：`CLAUDE.md` 称本项目「**也不需要 `tsconfig.json`**」（指运行不依赖它），
> 但该文件确实存在且含 `paths: {"@/*": ["./scripts/*"]}`。两者不冲突

### 🟢 P6：`brightness` 一节的字段名用的是上游 iztro 的

SKILL.md 称「`minorStars` / `adjectiveStars` 不带该字段」。本项目 `chart.palaces[].stars[]`
是**扁平数组 + `type` 字段**（`major` / `minor` / `sha` / `lucky`），并不存在
`minorStars` / `adjectiveStars` 这两个键。核心结论正确（实测：主星 14/14 带 `brightness`，
其余三类 0 颗带；取值仅 `bright` / `dim` / `normal` 三级），但字段名会让读者去找不存在的键。

### 后续修正（2026-09-19）：P1 的处置方向整个反了

上面 P1 的修复是**按错误的前提**做的：它把「仆役」当成项目的既定口径，于是让文档去迁就实现
（SKILL.md 补表 + 点明「第 8 宫是仆役、传交友会失败」）。

但复核发现**「仆役」根本不是本项目的口径，而是上游技术栈的口径泄漏**：

| 来源                                                        | 第 8 宫叫法 |
| ----------------------------------------------------------- | ----------- |
| iztro（排盘引擎）                                           | 仆役        |
| `reference/ziwei-samples-toolkit`（数据集）                 | 仆役        |
| `test/fixtures/charts.jsonl`（本项目基准快照）              | 仆役        |
| **`scripts/nihai/tianji.ts`（倪海夏《天纪》原文）**         | **交友**    |
| **`scripts/ziwei/constants.ts` 的 `PALACE_NAMES_ORDER`**    | **交友宫**  |

`algorithm.ts` 原文是 `name: p.name`——宫名**直通 iztro，内核从未做过映射**，
于是项目自己写好的十二宫名表成了**死代码**（全仓零 import）。

**已按「实现迁就项目口径」重做**：内核加 `IZTRO_TO_PROJECT_PALACE` 映射，
十二宫统一带「宫」字，第 8 宫改名**交友宫**；旧写法（仆役 / 交友 / 去「宫」字简称）
全部保留为 `--focus` 的别名。所以上表 P1 那一行的复验结论
（`--focus 交友` ❌）**已经失效，现在四种写法都 ✅**。

连带修掉三处会因此**静默失效或崩溃**的硬编码（都是这次才暴露的）：

- `purple-star.mjs` 的 `heming`：取宫用旧名 → 文本路径 TypeError 崩溃、
  `--json` 路径更早 `return` 故**静默输出空数组**（比崩溃更糟）
- `patterns.ts` 的「化禄入财」「化权入官」：取宫用旧名 + 有 `if (!c)` 守卫
  → 两个格局**永不触发**，不报错
- `test/lib/compare.mjs`：基准样本存的是 iztro 名，故在比对器里做一次**单向**宫名翻译

后两处的守卫是**本次新增**的（此前 `--focus` 与 `heming` 全仓零覆盖）：

| 新增断言                                            | 层  | 反向实验验证                                                       |
| --------------------------------------------------- | --- | ------------------------------------------------------------------ |
| 十二宫映射表与 `PALACE_NAMES_ORDER` 同集合          | 3   | 把「仆役」映射成「官禄宫」→ 红                                     |
| iztro 直连词法（不读映射表）                        | 3   | 同上 → 红                                                          |
| 十二宫偏移算术 `(命宫 − 本宫 + 12) % 12`            | 3   | 同上 → 红                                                          |
| 化禄入财 / 化权入官（按偏移算术核对，双向）         | 3   | 退回旧宫名 → 仅这两条红，层 1 的 304 条照旧全绿                    |
| `--focus` 四种写法聚焦到同一宫                      | 2   | 删掉一个别名 → 红                                                  |
| `heming --json` 派生字段与 chart 自洽               | 2   | 查找键退回旧名 → 仅这两条红                                        |

> **这次最有价值的一点**：把映射表故意改错，层 1 的 300 条基准**照旧全绿**——
> 因为比对器与内核共用同一张表，会一起错。这是 [README](README.md) 那条贯穿性教训
> （02 号：比对器与内核同源同错）的**又一次实证**，见
> [test/README.md 第二节第 6 条](../../test/README.md)。

改动后 `selftest` **44/44** ✅、`npm test` **346/346** ✅（8.1 秒）—— 本次纯文档改动，内核未动。

### 后续修正（二）（2026-09-20）：格局识别补测 —— 70 个格局名的独立预言机

**日期：** 2026-09-20
**被测对象：** `scripts/ziwei/patterns.ts`（1190 行 / 41 个 detect 函数 / **70 个格局名**）
**状态：** ✅ 已完成并固化进层 3

#### 为什么补

[test/README.md](../../test/README.md) 自述的六个盲区里，「格局识别」是**最大的一个**：
`patterns.ts` 是全仓行数第二多的文件，而它此前**没有任何基准** —— 只有第三节那次留下的
「化禄入财 / 化权入官」两条守卫，其余 40 余个格局零覆盖。

本次把 2026-09-19 那次建立的**安星法偏移算术**方法推广成一套覆盖**全部 70 个格局名**的
独立预言机，并按本项目的规矩做了**反向验证**（不反向验证过的断言不算数）。

#### 独立性从哪来：定位路径分岔

预言机若照抄实现的判定逻辑，就只是复读机。这里的分岔点在**「怎么从 chart 找到那几个宫」**：

| | 实现 `patterns.ts` | 预言机（层 3） |
| --- | --- | --- |
| 三方四正 | 地支算术 `[m, (m+4)%12, (m+8)%12, (m+6)%12]` | 宫名 `find(p => p.name === "财帛宫")` |
| 夹宫 | 地支算术 `(branch + 11) % 12` / `(branch + 1) % 12` | 宫名「兄弟宫 / 父母宫」 |
| 火贪 / 铃贪 | 正向枚举 `(tan.branch + 4/6/8) % 12` | 相对偏移取模 `(sha.branch − tan.branch + 12) % 12` |

宫名本身的正确性由层 3 **既有**的两条偏移恒等式独立保证（本次未新增，见
[test/README.md 第二节第 6 条](../../test/README.md)），所以这不是「用一个没验过的量去验另一个量」。

共 **50 项断言**：44 条单格局预言机 + 3 条派生名（按星名展开的 `*化禄入命` 等）+ 3 条输出结构。

#### 反向验证：6 种注入，各自的爆炸半径

每条断言都做过分注入验证 —— 注入后**只有目标断言变红，无误伤**：

| 注入点 | 变红项 | 说明 |
| --- | --- | --- |
| 三方四正 `(m+4)` → `(m+5)` | **14 项** | 杀破狼、机月同梁、三奇加会、双禄朝垣、廉杀羊、巨火羊…… |
| 夹宫 `(branch+11)` → `(branch+1)` | **6 项** | 日月 / 辅弼 / 昌曲 / 魁钺 / 空劫夹命、羊陀夹忌 |

#### 抓到的真实缺陷：「杀破狼」的 `palaces` 恒为空

新加的「每条 Pattern 的字段完整且取值合法」断言在 `1924-10-22 / 9 时 / female` 上炸出：

```text
1924-10-22 时9 female 的「杀破狼」：palaces 为空
```

**实测规模**：杀破狼的 86 次触发里，**55 次（64%）`palaces` 是空数组** —— CLI 会渲染出
「涉及宫位：」后面空无一物。这是**用户可见的输出缺陷**，不是内部字段问题。

**根因**：该字段用 `getMajorStarNames(p)[0]` 取**第一颗**主星来比对，而紫破 / 廉贪 / 武杀
这类**双主星同宫**极常见：

| 宫 | 主星数组 | `[0]` 取到 | 是否在 `has` 里 |
| --- | --- | --- | --- |
| 官禄 | `[廉贞, 贪狼]` | 廉贞 | ❌ |
| 财帛 | `[武曲, 七杀]` | 武曲 | ❌ |
| 命宫 | `[紫微, 破军]` | 紫微 | ❌ |

于是「七杀 / 破军 / 贪狼」一个都匹配不上，整张盘的宫位列表被清空。

**修复**：改为 `.filter(p => has.some(s => getMajorStarNames(p).includes(s)))` ——
与同文件 `detectJiYueTongLiang` 的**既有正确写法**对齐。只改**展示字段**，判定逻辑未动。

#### 效力边界（别高估）

- 只核对「**格局是否触发**」。`level` 分级、`description` 判词、`conditions` 文案**不覆盖**
- 预言机复刻的是**实现当前的口径**，不是照命理理想口径重写（见下条争议）
- 「昌曲夹命」「火铃夹命」在 300 条基准里触发 **0** 次 → 断言空转，已用
  `NO_HIT_IN_FIXTURES` **显式登记**（该集合里的格局若变成有命中，测试会失败并提示移除），
  这是「宁可显式失败，也不静默通过」的直接体现
- 另加一条**名册守卫**：输出里出现预言机表以外的格局名即失败，逼新增格局同步补预言机

#### 未决：火贪 / 铃贪的口径争议

`detectHuoTan` / `detectLingTan` 的命中条件实测为：

```text
贪狼与火（铃）同宫或会照  且  贪狼在命宫三方四正
```

**32 次命中里有 12 次，那颗煞星照不到命宫**。数学根因是一个容易想当然的点：

> **三方四正不是传递关系。**
>
> 命宫 `m` 的三方是 `{m, m+4, m+6, m+8}`。贪狼若在 `m+4`，**贪狼自己的**三方是
> `{m+4, m+8, m+10, m}` —— 与命宫三方差一个 `m+2`（对宫）。只有贪狼恰在命宫时两者才相同。
>
> 所以「贪狼会照火星」**不等于**「火星在命宫三方」。

实现 `conditions.required` 里明写的是两条：**「贪狼会照火铃」+「贪狼会照命宫三方」** ——
**代码与文档自洽**，故本次判定为**口径选择**而非 bug，预言机按实现复刻，并在测试代码注释里
显式记录了这一争议（含收紧方式：加一条 `SANFANG_NAMES.includes(sha.name)` 即可）。
**是否收紧留给项目方决定。**

#### 为什么补

到（二）为止，[test/README.md](../../test/README.md) 自述的盲区里只剩**合盘**没填：层 2 原有的
两条断言只守「`heming` 跑得通」与「`--json` 的派生字段与 chart 自洽」—— 那守的是**宫名查找
落空**（旧名会让 `--json` 静默输出空数组、文本路径抛 TypeError），**不是合盘的论断内容**。

#### 独立性从哪来：期望值与被测值走两条路

沿用（二）的思路，但分岔点换了一处 —— 这次是**「期望值由谁算」**：

| | 被测值 | 期望值 |
| --- | --- | --- |
| 来源 | CLI 子进程的文本 / `--json` 输出 | 测试进程内 `generateChart` 独立排盘 |
| 复算方式 | — | 安星法偏移恒等式 + 四化表查表 |
| 另一条交叉路径 | — | **交换 `--a-*` / `--b-*` 后的另一次运行** |
