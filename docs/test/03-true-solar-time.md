## 一、起因与一次前提更正

本报告起源于「要不要编程接入 taibu 做测试」这个问题。分析中发现**我先前说错了一个前提**：

| 我之前的说法 | 实情 |
| --- | --- |
| 「taibu 的紫微排盘是**完全独立的实现**」 | ❌ **错的**。taibu 也用 iztro |

证据：

| 事实 | 位置 |
| --- | --- |
| 全仓库（排除 `node_modules`）**只有 1 处** import iztro | `packages/core/src/domains/ziwei/shared.ts:5` |
| 排盘直接调 `astro.bySolar(...)` | 同文件 `:210` |
| 大限区间取 `palace.decadal.range`（iztro 给的） | `ziwei/calculate.ts:142` |
| **虚岁取 `horoscope.age.nominalAge`** | `ziwei-horoscope/calculate.ts:197` |

最后一条是致命的——它调的 `astrolabe.horoscope(targetDate)`（`:170`）与本项目 `invariants.test.mjs:243` 的预言机**是同一个函数**。拿 taibu「验证」虚岁，等于**拿 iztro 验证 iztro**。

所以 [02](02-core-nominal-age.md) 里那 5 个案例全对齐，证明的只是「本项目的修复让它与 iztro 对齐了」——这件事 `npm test` 里的预言机断言已在自动覆盖，taibu 没提供额外信息。**修复本身没错，错的是我给 taibu 的独立性强加了不该有的分量。**

### 结论：不建议编程接入 taibu

1. **同源**——能比的字段（星曜、宫位、大限、虚岁）全部来自 iztro
2. **唯一独立的面（真太阳时）不需要跑它**——那些结论全是**读源码对比公式**得出的，没执行过 taibu 一行代码
3. **接入成本高**——pnpm monorepo，要先走 tsc 构建；根仓库 AGPL-3.0、`packages/core` 是 MIT，许可边界要理清；且它是只读快照，不该进依赖图

## 二、但意外挖到了真东西：真太阳时口径不同

taibu 里**真正自己实现**的是真太阳时，而它与本项目**公式不一样**：

| | 本项目（默认） | taibu |
| --- | --- | --- |
| 公式 | `(经度 − 120) × 4` | `(经度 − 120) × 4 + 均时差` |
| 位置 | `purple-star.mjs:227-239` | `domains/shared/true-solar.ts` |

taibu 多算一项**均时差（equation of time, EoT）**。实测幅度：

```text
均时差范围：−14.6 ~ +16.5 分钟（2026 全年）
```

均时差会**把结果推过时辰边界**。扫描 1990 年北京（116.4°E）全年 × 每 10 分钟：

```text
48384 个采样点中，2496 个两边时辰判定不同（5.16%）

1990-01-07 09:20   本项目=巳   taibu=辰
1990-01-07 11:20   本项目=午   taibu=巳
```

**约 5% 的出生时间会排出两张不同的盘**——时辰变则命宫变，整张盘全变。

### 一处措辞收紧

我一度说「taibu 天文学上更严格」——**这个说法要收紧**。逐字比对后，taibu 的均时差公式与本项目**完全相同**：

```js
// taibu: packages/core/src/domains/shared/true-solar.ts:30
function equationOfTime(dayOfYear, year) {
  const isLeap = (year % 4 === 0 && year % 100 !== 0) || year % 400 === 0;
  const B = (2 * Math.PI * (dayOfYear - 81)) / (isLeap ? 366 : 365);
  return 9.87 * Math.sin(2 * B) - 7.53 * Math.cos(B) - 1.5 * Math.sin(B);
}
```

同一个 81、同一个 9.87 / −7.53 / −1.5、同一条闰年规则。它不是公式更精，只是**无条件计入**均时差而已。

**这是口径选择，不是谁有 bug**——均时差是真太阳时严格定义的一部分（真太阳时 = 平太阳时 + 均时差），而只做经度校正是传统排盘的常见口径。

## 三、设计取舍：默认**不加**均时差

关键约束：`selftest` 与 `test/cli.test.mjs:48-60` 对真太阳时**已有断言**，写死了「只含经度项」：

```js
eq(t.offsetMinutes, Math.round((lx.longitude - 120) * 4));  // ← 默认开启均时差时必然变红
```

所以默认值不是随便的选择：

| 方案 | 后果 |
| --- | --- |
| **默认不加**（采用） | 现有盘、`selftest`、`cli.test.mjs` 全部零影响；传统口径为默认，符合倪师取向 |
| 默认加 | `selftest` 石家庄那条断言必红，且此前排的所有盘都变（5.16% 会换时辰）——正是 [02](02-core-nominal-age.md) 那类**静默行为漂移**的翻版 |

均时差用 `--eot` 显式开启。

**改动点：**

- 新增 `equationOfTime(year, month, day)`，工程近似式 `9.87·sin2B − 7.53·cosB − 1.5·sinB`
- `calcTrueSolar(clockHour, clockMinute, longitude, { eot })` 加第 4 参，返回值增加 `eotMinutes`，**现有判定逻辑一行不动**
- `buildBirthInfo` 读取 `--eot`，`hourNote` 写清构成
- **不改的**：`--branch` 路径不受影响（直接指定时辰，本就跳过校正）；`test/lib/compare.mjs` 也不动（基准样本 `longitude` 恒为 120 且走内核直调，不经过 CLI 校正）

## 四、实现中发现并修掉的一个真问题

**分项取整 ≠ 先加后取整。**

原写法是先把两个偏移量相加再取整：`Math.round(-14.4 + 3.8) = -11`。但提示文案要分项展示，就会写成「经度 **-14** + 均时差 **+4** = **-11**」——用户一看就像算错了（`-14 + 4 = -10`）。

**选择改实现而非改断言**：

- `offsetMinutes = longitudeMinutes + eotMinutes`（分项取整后相加，保证文案自洽）
- **但时辰判定仍用未取整的 `longitudeRaw + eotRaw`**（保证默认口径与旧实现逐位相同，不存在行为漂移）

另加一道防御：均时差依赖具体日期，缺失会静默算出 `NaN`。现在 `--eot` 缺 `year/month/day` 会**直接抛错**——符合本项目「宁可启动失败，也不静默产出错盘」的立场。

## 五、实测效果

同一个出生时间 `1990-01-07 09:20 北京`，两种口径排出的是**两张不同的盘**：

```text
默认：  钟表 09:20 → 真太阳时校正 -14 分 → 巳时(09:00-11:00) · 命宫 申 · 身宫 午
--eot： 钟表 09:20 → 真太阳时校正 经度 -14 分 + 均时差 -6 分 = -20 分 → 辰时(07:00-09:00) · 命宫 酉 · 身宫 巳
```

十二宫完全重排（命宫申→酉）。**这不是小数点级差异，是换了一张盘**——所以做成显式开关而非静默启用。

**注意：均时差与经度无关。** 即使 `--lng 120`（标准经线），开了 `--eot` 照样有校正。所以「`--lng 120` = 不做校正」这个直觉只在默认口径下成立——`help` 文案也已相应改为「默认 120，即不做**经度**校正」。

## 八、⚠️ 悬置未修：显示值 vs 判定值的缝隙

**taibu 的同类问题**：同一案例它输出

```text
correctionMinutes: -20.7   trueSolarTime: "08:59"   trueTimeIndex: 4
```

它**显示 −20.7，却应用了 −21**（09:20 − 21 = 08:59）——显示与判定不自洽。

**本项目也有同类的残留**（同一案例）：

```text
钟表 09:20 → 真太阳时校正 -20 分 → 辰时(07:00-09:00)
```

精确值是 **−20.668**，判定用它 → 539.33 分，落在 540（巳时界）**之下**，故为辰时。**但用户按显示的「−20 分」去算：09:20 − 20 = 09:00，那正是巳时的界——读出来的结论与实际结果相反。**

修复时修掉的是「分项取整的加和不自洽」，这个「显示值 vs 判定值」的缝隙**没修**，只在时辰交界 ±0.5 分内露头。

**可选修法**：显示精确到 0.1 分，或在交界处加一句提示。

## 九、这次交叉验证能对准什么（衔接 [04](04-crossval-taibu.md)）

真正**独立实现**、因而不是复读机的，只有这几处：

| 可比项 | taibu | 本项目 | 独立性 |
| --- | --- | --- | --- |
| **时辰边界映射** | `floor((hour+1)/2)` | `floor((solar−60)/120)+1` | ✅ **两套独立写法** |
| **取整时机** | 先相加 → `round` → **再应用** | 判定用**未取整**值 | ✅ 方法不同 |
| 晚子时口径 | `hour>=23 → 12` 无条件 | 默认 0，`--late-zi` 才 12 | ✅ 可对 |
| 均时差公式 | 同上 | 同上 | ❌ **逐字相同** |
| 排盘 | iztro | iztro | ❌ **同源** |

也就是说，交叉验证**能抓「应用层」的 bug，抓不到「公式层」的**。成色有限，但确实抓到了真东西——见 [04](04-crossval-taibu.md)。
