# 04 · 交叉验证报告 · 本项目 vs taibu

**日期：** 2026-09-19
**被测对象：** 排盘层——`scripts/ziwei/algorithm.ts` 与 taibu 的 iztro 集成层
**对标物：** `reference/taibu/`（只读快照）
**状态：** ✅ 排盘层通过；✅ 挖出的 bug（真太阳时跨午夜不回退日期）**已修复并复验**——修复后重跑同一探针，**126/126 全部一致，分歧归零**（见第七节）

---

## 一、结论

**1. 排盘层通过验证。** 给定相同的 (公历日期, 时辰序号, 性别)，本项目和 taibu 排出的盘**逐字段相同**——126 例中日期与时辰都一致的 103 例，**星曜分歧 0**。两边 `bySolar(date, hour, gender, true, 'zh-CN')` 调用逐字相同，这是预期结果，现在有了实证。

**2. 但找到一个真 bug，且它在两边调用逐字相同的前提下依然存在。** 真太阳时校正把时刻推出当天时，**本项目不调整日期**。126 例中 23 例命中，时辰全部一致、**日期差一天**。这不是表示层差异，是排盘错误：日期错一天 → 农历日错 → 紫微星定位错 → **十二宫 12/12 全部不同**。

---

## 二、验证方法与效力边界

### 能验证什么、不能验证什么

taibu 与本项目都基于 iztro（见 [03](03-true-solar-time.md) 第一节的前提更正）。拿 taibu 验证「iztro 排得对不对」是**无效验证**——同源。这次验证的真正对象是**各自的 iztro 集成层**：日期怎么定、时辰序号怎么算。这部分两边独立实现，可比。

### 决定性事实

```js
// 本项目 algorithm.ts:106
astro.bySolar(solarDate, hour, iztroGender, true, "zh-CN")
// taibu shared.ts:272
astro.bySolar(dateStr, trueSolarTimeInfo.trueTimeIndex, genderStr, true, "zh-CN")
```

同签名、同 `true`、同 `'zh-CN'`。所以给定相同的 (公历日期, 时辰序号, 性别)，两边的盘**必然逐字节相同**——差异只可能来自**日期**或**时辰序号**。

### 口径对齐（不对齐就是比口径而非比实现）

| 项 | taibu | 本项目 | 对齐方式 |
| --- | --- | --- | --- |
| 均时差 | 无条件计入 | 默认不计 | 本项目加 `--eot` |
| 23:00–23:59 | 恒映射 timeIndex 12 | 默认早子时 | 本项目加 `--late-zi` |
| 日期 | 跨午夜时回退/前进 | **不调整** | ← 被验证出来的差异 |

### 探针自身修过三处（避免把探针 bug 当成真分歧）

1. taibu 的 `solarDate` **不补零**（`1990-1-7`），直接比字符串比的是格式——两侧归一化成数值三元组再比
2. 亮度口径不同（见第五节）——把 taibu 的 7 级按本项目映射塌缩后再比
3. `soul` 字段**不是命宫支**，是命主（破军）；命宫支在 `earthlyBranchOfSoulPalace`。第一版探针标签写错，已核实更正

### 让 taibu 在 Node 下直接跑

taibu 按 TS 惯例写 `./shared.js` 而磁盘上是 `.ts`，Node 不会自动重映射。注册一个解析钩子：相对路径的 `.js` 若同名 `.ts` 存在就改指 `.ts`。裸包名（`iztro` / `lunar-javascript`）不用管——`reference/taibu` 在本仓库内，Node 向上查找会命中本项目的 `node_modules`（iztro 2.6.1）。

## 四、根因：日期被丢在 `calcTrueSolar` 内部

`purple-star.mjs:264`：

```js
const solar = (((clockMins + longitudeRaw + eotRaw) % 1440) + 1440) % 1440;
```

这个 `% 1440` **把跨天的信息当场销毁了**。函数只返回 `branch` / `isLateZi`（`purple-star.mjs:255-277`），调用点（`:466`）拿到后只设 `hour`，`info.day` 始终是钟表日期。

于是 `(info.day, hour)` 这个组合指向的**不是出生时刻**：

```text
输入：1990-05-15 00:30 喀什（75.99°E，经度校正 −176 分）
真太阳时实际是 前一日的 21:34

taibu：  日期 1990-05-14   timeIndex 11（亥时）   ← 完整 datetime，自洽
本项目： 日期 1990-05-15   hour 11（亥时）        ← 日期用钟表轴、时辰用真太阳时轴
```

混用两套时间轴。`(05-15, 亥时)` 在真实时间轴上比出生时刻晚了约 9 小时。

### 级联后果实测（同一例）

```text
公历   我 1990-05-15        它 1990-05-14
农历   我 四月廿一           它 四月二十
紫微   我 申                它 未
        → 十二宫中星曜排布不同的宫位：12 / 12
命宫   我 午                它 午     ← 唯一没变的，因为命宫只依赖生月+生时
```

### 东部的对称情形，且 `--late-zi` 救不了

哈尔滨 1990-05-15 23:30（126.6°E，校正 +30 分 → 真太阳时次日 00:00）：

```text
① 默认           公历 1990-05-15  农历4月21日  hour=00  紫微=辰
② --late-zi      公历 1990-05-15  农历4月21日  hour=00  紫微=辰   ← 与①完全相同
③ 手工填次日      公历 1990-05-16  农历4月22日  hour=00  紫微=酉   ← 与 taibu 全等
taibu            公历 1990-5-16   农历四月廿二  timeIndex=0  紫微=酉
```

原本预期 `--late-zi` 会通过 timeIndex 12「安星按次日」顺带把东部这一侧救回来——**实测不成立**。校正后 `isLateZi` 已是 false（真太阳时 00:00.1 不落在 23:00–23:59），`--late-zi` 成为空操作，`lateZiCandidate` 也是 false，**连晚子时提醒都不输出**。用户输入 23:30 却得不到任何提示。

## 五、表示层差异（不是缺陷，但建议登记）

这两处**不是分歧**，是口径不同。第一版探针把它们混进了「星曜不同」，那是探针的 bug。

### 1. 亮度：7 级 vs 3 级

| | iztro 原始 | 本项目 | taibu |
| --- | --- | --- | --- |
| 主星 | 庙旺得利平不陷 | 塌缩为 `bright`/`normal`/`dim` | 原样透传 7 级 |
| 非主星 | 同上 | **不输出该字段** | 原样透传 |

本项目的映射（`algorithm.ts:31-36`）：`庙/旺→bright`、`陷/不→dim`、**其余（含 得/利/平）→normal**。

两处值得留意：

- **`brightness` 只给主星填**（`algorithm.ts:114-128`），`minorStars` / `adjectiveStars` 完全不填。所以探针里出现「我 `文昌||` vs 它 `文昌|利|`」这类——是**本项目信息更少**，不是排错了
- `利` 落到 `normal` 兜底，但 SKILL.md 的庙旺利陷口径只写了「`normal` = 平」。**文档与实现不一致**，`得`/`利` 的归属没交代

### 2. 宫位标识

taibu 用中文字支，本项目用 0-11 索引（`branch`）。探针按 `BRANCHES[branch]` 建索引对齐——**这同时验证了 `chart.palaces` 那个「寅起的地支数组序」是自洽的**，103 例逐宫正确匹配。

## 六、修复设计（bounded，已批准并实施）

`calcTrueSolar` 生产环境只有**一个**调用点，日期经 `info` 单点流入（`fmtDate` 格式化成 `solarDate`），所以这是个局部改动。

**1. `calcTrueSolar` 增返 `dayOffset`**

```js
const totalRaw = clockMins + longitudeRaw + eotRaw;
const dayOffset = Math.floor(totalRaw / 1440);
const solar = ((totalRaw % 1440) + 1440) % 1440;
```

`branch` / `isLateZi` / `solar` 的算法**一位不动**——那是刚通过 126 例验证的口径。`dayOffset` 也取**未取整**值：跨没跨过午夜由精确时刻决定，先取整再判断会在边界翻车。

**2. 新增 `shiftDate`，用日历运算调整日期**

```js
function shiftDate(year, month, day, days) {
	const d = new Date(Date.UTC(year, month - 1, day + days));
	return { year: d.getUTCFullYear(), month: d.getUTCMonth() + 1, day: d.getUTCDate() };
}
```

用 `Date.UTC` 而非 `day ± 86400000`——跨月、跨年、闰年交给它算，且 UTC 无夏令时。下游（农历、排盘、合盘、流年）经 `info` 自动跟随，**无需逐处改**。

**3. 提示文本显式说明日期变化**

实际输出（喀什例）：

```text
【命盘总览】 1990-05-14 钟表 00:30 → 真太阳时校正 经度 -176 分 + 均时差 +4 分 = -172 分 → 亥时(21:00-23:00)（真太阳时已跨过午夜，出生日期回退至前一日 1990-05-14） · 男 · 经度 75.99°E
```

日期变了必须说，否则用户看到盘与输入的 `--date` 不符会以为排错了。

**4. 不设 `--no-date-roll` 开关**

「只校时辰不校日期」不是任何一派的传统口径，是实现疏漏。按项目「不做静默切换、不给错误默认值留活路」的立场，直接修正。

**5. 测试（先写断言，后改实现）**

- `selftest` 增 **4 条**：西侧回退（喀什 00:30 → 前一日 21:38 亥时）、东侧前进（哈尔滨 23:30 → 次日 子时）、不跨天时 `dayOffset` 恒 0、以及一条**自洽性不变量**（`dayOffset × 1440 + solarMinutes` 必须还原回「钟表时刻 + 校正量」）
- `test/cli.test.mjs` 增 **3 条**端到端，基准用的是**等价性**而非写死的星曜值：跨天自动调整的结果，必须等于**手工输入校正后日期**的结果。这条基准与实现走两条不同的输入路径，不依赖内核自证
- `npm test` 的基准比对部分**未受影响**（样本 `longitude` 恒 120，无跨天），符合预期

### 一处实现时的判断（对应修复设计的第 6 点）

东部前进后 `isLateZi` 变 false，`lateZiCandidate` 随之变 false，**晚子时对照段确实不再输出**——这是对的，不是漏提醒。理由：校正后确已过午夜，早/晚子之争自然消解，此时再给一个「晚子时算次日」的对照，等于提供一个**已知错误**的备选口径。

取而代之的说明放在**日期提示链里**（上面第 3 点的输出），它直接解释了「为什么你输入的 `--date` 和盘上的日期差一天」——比在 `lateZiSection` 里补一句更对症。

顺带收紧了一处措辞：`lateZiSection` 的提醒原文是「**你给的钟表时间**落在 23:00–23:59」，但 `lateZiCandidate` 的真实含义是**校正后**的真太阳时落在该区间。开 `--eot` 或西部城市时两者会分家（喀什 02:30 校正后是前一日 23:37），故改为「校正后的真太阳时落在 23:00–23:59」。
