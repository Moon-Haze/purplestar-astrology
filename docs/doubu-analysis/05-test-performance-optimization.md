# 05 · 测试套件性能分析与优化

> 目标：在不损失断言语义的前提下，把 `npm test` 的墙钟压下来。方法纪律是「无 profile 不结论、无 A/B 不承诺收益」。

## 1. 基线测量

环境：Node v22.23.2，iztro 2.6.1，lunar-typescript 1.8.6，Linux x64。

### 1.1 产品代码冷启动

| 路径                                             | 实测耗时 | 结论                                       |
| ------------------------------------------------ | -------- | ------------------------------------------ |
| 单次 CLI 冷启动（`node purple-star.ts analyze`） | ~1.0s    | 瓶颈在进程初始化                           |
| 仅 `require("iztro")`                            | ~0.45s   | iztro 安星+星曜数据固有成本                |
| 深层 `require("iztro/lib/astro")`                | ~0.45s   | 与全量相同 → REJECT 深层导入               |
| `generateChart` 稳态（已加载后）                 | ~15ms/次 | 全量 51.8 万条约 2.16h（与文档 2.3h 吻合） |

结论：产品侧冷启动税来自 iztro 本身，深层 import 无收益，不改。

### 1.2 测试套件墙钟

完整 `npm test`：450 项，**90.2s**。分层耗时：

| 层                  | 项数   | 墙钟      | 占比    |
| ------------------- | ------ | --------- | ------- |
| 层 1 排盘对标       | 304    | 5.4s      | 6%      |
| **层 2 CLI 端到端** | **45** | **66.4s** | **74%** |
| 层 3 排盘结构不变量 | 82     | 3.2s      | —       |
| 层 4 三合派约束     | 6      | <0.1s     | —       |
| 层 5 数据源纯函数   | 13     | 1.9s      | —       |

**瓶颈定位**：层 2 的 45 个用例每个 `it` 都 `execFile("node", ["purple-star.ts", ...])` 起一个真子进程，每个子进程付 ~0.95s 的 iztro 冷启动。67 次子进程 = ~64s，与实测吻合。

## 2. 候选方向裁决

### T1 · 全局子进程参数缓存 —— REJECT

做法：给 `cliCmd` 加 LRU，相同参数直接复用上次子进程 stdout。
实测：子进程数 67 → 63（**仅省 6%**）。
拒绝原因：CLI 测试刻意用不同 `--date/--time/--city/--focus` 覆盖不同分支，参数重复率极低，缓存命中率天然差。改动已回滚。

### T3 · CLI 测试进程内直调 —— ACCEPT

做法：把 `cliCmd` 从「起 node 子进程」改为「在测试进程内直接调 `COMMANDS[sub](parseArgs(args), ctx)`」——这正是 `purple-star.ts main()` 的内部逻辑。`parseArgs`、`buildBirthInfo`（真太阳时/城市解析/晚子时）、各 cmd 业务逻辑**全部仍被测**，只省掉「每个用 fork 一个进程」的冷启动税。

| 指标            | Baseline   | Candidate（进程内默认） |
| --------------- | ---------- | ----------------------- |
| 层 2 CLI 45 项  | **154.0s** | **4.7s（33×）**         |
| 全量 `npm test` | 90.2s      | **18.0s（5×）**         |
| 断言结果        | 450 全绿   | **450 pass / 0 fail**   |

## 3. 三道验证（缺一不可）

1. **语义 oracle**：选 5 个代表 case（含真太阳时 `--city 哈尔滨`、晚子时 `--time 23:30`、流年 `--liunian`、多 view topic），进程内 `COMMANDS[sub]` 返回值 vs `execFile` 真子进程 stdout，**逐字节一致**（仅差 `console.log` 尾部一个 `\n`）。
2. **真子进程冒烟保留**：「内核直调 ≡ CLI --json 输出」断言强制走真子进程（`cliReal()`，~2.5s，仍在最慢项里），持续盯「测试进程内的内核」与「线上 CLI 子进程」不漂移——进程内路径替代不了它对子进程入口的覆盖。
3. **回退兼容**：设 `CLI_SUBPROCESS=1` 强制全子进程，450 仍全绿（142s）；`npm run typecheck` 通过。

## 4. 工程取舍

- 默认走进程内（快）；`CLI_SUBPROCESS=1` 可切回全子进程用于回归。
- 代价：大部分用例不再走真子进程，对子进程入口的覆盖从「逐用例」收敛成「1 条常驻冒烟」。这是测试速度 vs 覆盖粒度的可接受交换——子进程入口本身极薄（`parseArgs` → `fn` → `console.log`），厚逻辑全在 cmd 函数里，而那部分进程内照常测。
- 一个实现坑：静态 `import "@/cli/args"` 会在 hooks 注册**之前**的 ESM 解析阶段失败，必须改动态 `import()`（运行时才解析，此时 `registerHooks` 已就位）。

## 5. 未做的方向（候选账本）

- C2 V8 编译缓存 / `--code-cache`：启动税主要在 iztro 数据加载而非 V8 编译，预期收益小。
- C4 批量核验并行：层 1/3 已是函数调用，无子进程可并行。
- C6 相邻盘增量：排盘 15ms/次，非瓶颈。
