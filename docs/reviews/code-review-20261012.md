# 代码审查标准与流程（2026-10-12）

> **适用范围**：本仓库（单 skill 形态）一切代码 / 内容 / 文档变更。
> **评审边界**：架构分层、体系口径（文墨排盘 + 倪师论断）、参数面语义等**既定决策**不在评审范围内 ——
> 评审查的是「实现是否忠实于决策」，不是「决策是否正确」。要挑战决策，走 ADR，不走代码评审。
> **与既有文档的关系**：`CLAUDE.md` 说**是什么、怎么组织**；本文件说**怎么审、审到什么程度算完**。
> 两者冲突时以 `CLAUDE.md` 为准，并回头修本文件。

---

## 0. 一条总则：机器已经查了的，人不要重复查

本仓库的自动化守卫密度异常高（七层基准回归 + 冻结内核契约 + 引文守卫 + 层 6 仓库自洽）。
**评审人力最贵的部分是注意力**，把它花在机器已经覆盖的地方等于净损失。

| 该由谁查             | 内容                                                                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **机器（已有守卫）** | 类型自洽 · 基准回归 · 内核契约符号与元数 · 绊线未被填回 · 引文分级 · 测试登记一致性 · 解析钩子候选序 · skill 自包含                                   |
| **机器（本次必跑）** | `typecheck` / `selftest` / `npm test` / 重构类的逐字节对拍                                                                                            |
| **人 / 评审 Agent**  | **语义是否正确** · **抽象边界是否划在正确的位置** · **常量是否身兼多职** · **新断言是否真的有独立性** · **文案是否得体且引文可溯** · **证据是否够格** |

一句话判据：**「这句话能不能被写成一条断言？」** 能，就交给守卫；不能，就亲自看。

## 1. 审查维度（五轴）

### 1.1 边界与契约

- 改动是否**越过了声明的冻结面**？冻结内核（`generateChart` / 宫位关系查询 / 四化查询 / 亮度查询 /
  `types.ts` 契约区块，见 `types.ts` 顶部的冻结注释）**只读不写**。插件可以**引用**冻结数据，
  不可以把数据**搬进插件**（见本次 `SchoolAdapter` 的"引用而非迁移"决策）。
- 新增扩展点时，**接口是不是真的接缝**？判据：加一个实现是否只需「一个文件 + 一行注册」。
  若还要改 3 处以上分发逻辑，那不是接缝，是把耦合换了位置。
- 是否引入了**第二个真相源**？两个地方都能改同一事实，就是下一次漂移的伏笔。
- 依赖方向是否单向？`cli/` 之间不得成环。

### 1.2 正确性与证据

- **每条结论都要有证据形态**：断言 / 逐字节 diff / 计数 / 反向注入实验，四者之一。
  「应该没问题」「看起来对」不是证据形态，直接退回。
- **新断言是否有独立性**？这是本项目最贵的教训（见 `test/README.md` §5、§6）：
  期望值若与被测实现同源同路径，那条断言只是实现的复读机，**任何数量的这类断言都不能替代一条外部预言机**。
  评审必问：**这条断言的期望值，是从哪条独立路径算出来的？**
- **反向验证做过没有**？注入一个已知失效，确认只有目标断言变红。没做反向验证的断言，
  可能压根没在测你想测的东西。

### 1.3 结构与抽象

- **一个常量是否同时承担了两个角色？** 这是本项目付出真实代价才修掉的问题
  （`TOPIC_KEYS` 既是运行时主题注册表、又是数据集物理列清单 → 加一个别名视图主题就让整条数据集工具链报
  `column not found`）。判据：**这个名字被用在哪里？各处的期望含义一致吗？**
- 抽象是否**justify 它的复杂度**？每个新抽象都要能回答"删掉它会多写几行"。答不出就别加。
  本项目已因此**否决**过"13 个 `analysis/topics/<key>.ts` case 文件"方案（数据驱动引擎里，
  造 per-topic 文件是纯碎片）。
- 是否只是把代码**换了位置**而不是减少？（派生关系、同步副本的搬家不算重构成果）
- 新增并行手维护表 = 退回 1.2 的真相源问题。派生优于手抄。

### 1.4 一致性与可维护性

- **计数不写死**：主题数、测试项数、断言数、层数 —— 能自报的自报、能派生的派生。
  评审见到硬编码的计数即提问。
- **生成文件不手改**：`scripts/corpus/data/manual/*.ts` 是 `tools/db/export-manual.ts code` 的产物。
  手改会在下次重跑被静默覆盖。改生成器，不是改产物。
- **风格跟随邻近代码，不追随格式化工具**：本仓库有大量 `{return x;}` 单行块；`prettier` 未被强制执行。
  跑一次 `prettier --write` 会改写**大量未触及**的代码（本仓库有大面积文件本就不合它的口径），
  制造与本次变更无关的 diff。
  只格式化本次真正新增/改动的行。
- 注释是否解释了**为什么**，而不是复述**做了什么**？刻意设计（如晚子时、缺口字段）必须在注释里点名，
  否则下一个人的第一反应是"这是 bug"。

### 1.5 表达与内容（文案 / 引文 / 文档）

- **引文纪律**：文案里凡出现「倪师 / 倪海厦 +「…」」形态，即被 `selftest` 知识分级守卫抽取，
  必须在 `scripts/analysis/grades.ts` 登记档位。
- **占位内容不得挂倪师引语**。自撰 / 占位文案挂引语属**伪造引文**，
  是评审必须拦下的一类问题（不是"忘了登记"，是根本不该这么写）。改为自述式说明。
- 改 CLI 的参数名或输出格式，`SKILL.md` 及其 `references/` 必须同步（那是可执行的行为规范）。
- 文档里的数字、路径、命令要能跑。写完自己敲一遍。

## 2. 按变更类型的审查分档

审查深度由**变更性质**决定，不由代码行数决定。判错档次的代价是过度审查（浪费）或审查不足（漏）。

| 变更类型                      | 必查                                                                       | 最低证据                                         | 档位 |
| ----------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------ | ---- |
| **修 bug**                    | 1.1 / 1.2 全查；是否有**能复现原缺陷**的断言；是否引入了只对本次有效的特判 | 新断言 + `npm test` 不降 + 内核层 117 不动       | 严   |
| **重构（声明不改行为）**      | 1.3 / 1.4；每个抽象的 justify；是否只是搬家                                | **逐字节对拍全场景**，失败场景数与新增场景数对齐 | 严   |
| **功能新增**                  | 1.1 边界；1.2 证据；新表/新常量的角色是否单一                              | `selftest` + `npm test` + 新增路径的端到端覆盖   | 中   |
| **内容 / 文案新增**           | 1.5 引文分级；口径是否与体系一致                                           | 引文守卫零违例 + 分级登记                        | 中   |
| **纯格式 / 注释 / 文档**      | 有无夹带语义变更；生成文件是否被手改                                       | `typecheck`（若动了 `.ts`）+ 肉眼确认 diff 范围  | 轻   |
| **依赖变更（iztro / lunar）** | `package.json` 的 pin 是否被改写；亮度口径是否整体位移                     | `selftest` **与** `npm test` 都跑 + 升级流程核对 | 严   |

> 「重构不改行为」在本项目有硬性含义：**必须**跑逐字节对拍。没跑 = 证据不完整 = 退回。

## 3. 严重度分级

| 级别     | 含义                                                         | 处置                                     |
| -------- | ------------------------------------------------------------ | ---------------------------------------- |
| **阻断** | 会产出错误结果 / 破坏冻结面 / 证据造假（守卫被削弱而非补强） | 必须修复后才能合入，不接受"后续补"       |
| **严重** | 架构边界被削弱 · 真相源分叉 · 新断言无独立性 · 缺证据形态    | 必须修复，或在评审记录里显式记为已知债务 |
| **建议** | 可读性 · 命名 · 抽象层次 · 文档同步                          | 作者自行决定；建议同批处理               |
| **记录** | 无即时影响但值得留档的观察                                   | 记入评审文档，不改代码                   |

> 词表刻意简化：架构评审沿用 `Strong / Worth-exploring / 可缓`，**代码评审**只用上面四级。
> 分级通胀会让真正的阻断项被淹没 —— 宁可多列一条建议，也别把阻断降格。

分级判据：**先问「它会怎样出错」，而不是「它有多丑」**。丑但不出错 → 建议；不出错但会让下一个错误
静默通过 → 严重。

## 4. 证据要求

**不接受"应该没问题"。** 交付前必须齐备：

| 证据                | 门槛                                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| `npm run typecheck` | **0 错误**。注意它只保证类型**自洽**，不保证类型**标得对**（`any` 也全绿）                               |
| `selftest`          | 全通过                                                                                                   |
| `npm test`          | 计数**只增不减**；**内核层（层 3 = invariants + kernel-contract）必须与基线一致**（基线值见执行计划 §9） |
| 逐字节对拍          | 重构类必做；既有场景输出逐字节一致                                                                       |
| 冻结面核对          | `git status` 确认冻结内核文件 0 改动                                                                     |

### 4.1 验证手段本身也要被验证

一条反直觉但本项目已付出代价的纪律：**验证脚本出的红灯，先怀疑验证手段**。

本次实例：逐字节对拍中途快照目录被清空，`cmp` 对两个**都不存在**的文件返回失败，于是 9 个场景
全部报 `DIFFERS`。若不复查，这会变成一次"改动破坏了全部输出"的假结论，并进而否掉一次正确改动。

判据：**当验证结果与常识强烈冲突时**（大面积变红、大面积变绿），先确认验证手段自身成立
（文件在不在、命令是否真跑了、退出码取自管道末端还是末端命令），再下结论。

### 4.2 计数口径

「测试没变少」要看**哪一层**：总项数会被新增插件项合法抬高，**内核层 117 不动**才是越界的信号。
评审时不要拿总数当护栏。

## 6. 流程

### 6.0 角色：作者与评审者必须分离

本仓库是单人主导（作者即绝大部分提交者），**最现实的风险不是没人审，而是自己审自己** ——
作者与评审者共享同一套心智模型时，作者的盲区会原样变成评审者的盲区，这条通道不存在。

因此：

- **作者**（人或 Agent）只负责 §6.1 自查，**不给自己开通过票**。
- **评审者**应当是另一方：人审 Agent 的产出，或换一个 Agent 会话（不带上作者的推理过程）审。
  换个会话的作用不是形式 —— 它切断的是"作者以为已经处理妥当"的上下文。
- 若确实只能自审（改动极小），则**必须改用反向提问**：假设这条改动是错的，列出它会怎样出错，
  再逐条去证伪。这比"检查一遍是否正确"更容易发现真问题。

### 6.1 提交前自查（作者 / 执行 Agent）

**先跑工具**，它按 §2 自动分档、执行该档必跑的闸门，并把下面两份清单打出来：

```bash
npm run review                                  # 对工作区未提交改动
npm run review -- --base master                # 对某基线的差异（含已提交部分）
npm run review -- --no-run                     # 只出分档与检查单，不执行闸门命令
npx tsx tools/review-gate.ts --byte-diff --no-run # 追加「逐字节对拍」（重构类必做的证据）
```

工具会给出：① 判定分档（严 / 中 / 轻）与依据；② 机检硬项（每条附文件与行号）；
③ 工具答不了、必须人看的判断题工作单。它**不替代**下面这些，它只跑它们并核对结果：

```bash
npm run typecheck                              # 0 错误
node scripts/purple-star.ts selftest           # 全通过
npm test                                       # 计数不降；内核层与基线一致（工具已核对）
git status --porcelain <冻结面文件列表>        # 应为空（工具也会报冻结面越界）
```

把「跑了什么、结果是什么」写进提交信息。

> ⚠️ **传参必须带 `--`**：`npm run review -- --byte-diff`（`--` 之后才是脚本参数）。
> 写成 `npm run review --byte-diff` 会被 **npm 自己**吃掉并报 `EUNKNOWNCONFIG` ——
> 看着像工具坏了，其实是 npm 的参数解析。同一坑也见 CLAUDE.md 的旗标面。

> ⚠️ 工具的已知边界（它自己不做的事，别指望它）：不重复实现引文分级的**判据**
> （那是 `selftest` 的权威，它只**指出新增行里哪些长得像倪师引句**）；不重跑任何断言；
> 不做风格判断；不给判断题代答。

> **关于 `--byte-diff`**：它把改动 stash 掉取基线，跑同一批场景（chart `--json`、
> `--report`、默认概览、**注册表派生的全部主题**）再逐字比对，17 个场景。
> 场景清单由 `TOPIC_KEYS` 派生而非手维护 —— 加主题时自动跟上。
> 三条设计都是本会话踩坑换来的：快照落**仓库内** `.review-tmp/`（`/tmp` 会被清空）；
> 读快照**先校验非空**，校验不过报「验证手段失准」并失败，**绝不**报成 DIFFERS；
> stash 用 `try/finally` 还原并**核对**工作区与对拍前一致，否则结论作废。
> 它只对「重构（不改行为）」有意义 —— 行为新增本来就该变。

**自查不等于评审**：自查只确认「没红」，不确认「红得对不对、够不够」。
自查的绿灯**不能**作为跳过评审的理由 —— 它恰好是作者最容易自我说服的地方。

### 6.2 何时必须评审

- 触及**冻结面 / `scripts/types.ts` 契约区块**
- 触及**真相源**（`TOPIC_DEFS`、`args-table`、`annotations.ts`、`grades.ts`）
- **重构类**变更（声明不改行为）
- 引入**新抽象 / 新注册表 / 新扩展点**
- **依赖变更**
- 变更**跨 3 个以上文件**或**跨层**（`cli/` ↔ 内核 ↔ `test/`）

轻量变更（注释、文档、局部文案）可跳过评审，但**不得夹带**上述类别的改动。

### 6.3 评审产出

评审结论落成文档，沿用既有评审文体（`docs/reviews/structure-review-20261011.md` 的分级候选写法）：

- 按严重度列条目，每条给**证据**与**处置建议**
- 明确写出**评审边界**（哪些刻意设计被排除在评审外），避免下一个读者误改
- 已采纳 / 已否决 / 记为债务，三态写清

### 6.4 评审报告模板

```markdown
### 候选 N · <一句话标题>　【阻断 | 严重 | 建议 | 记录】

**问题**：<在哪一行 / 哪个常量 / 哪个断言>
**判据**：<为什么这是问题 —— 最好是「它会怎样出错」，不是「它不好看」>
**证据**：<已经跑过什么，或如何构造反向验证>
**建议**：<最小修法>
**状态**：✅ 已实施 / ⏸️ 记为债务 / ❌ 已否决（理由：…）
```

## 7. 反模式（评审时不要做的事）

- **为了"更干净"而重排未触及的代码**：制造与变更无关的 diff，让真正的改动被淹没。
- **审查已被守卫覆盖的代码**：`npm test` 通过后再逐行核对一遍基准比对逻辑，是纯浪费。
- **在代码评审里推翻架构决策**：那是 ADR 的事。见开头的评审边界。
- **用"改大范围了所以要多测几句"替代逐字节对拍**：范围大小不改变证据形态的要求。
- **把红灯当结论**：见 §4.1 —— 先确认验证手段自身成立。
- **给建议级问题开阻断票**：分级一旦通胀，真正的阻断项就会被淹没。
