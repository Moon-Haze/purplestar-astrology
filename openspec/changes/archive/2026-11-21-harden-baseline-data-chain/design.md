# Design

## Context

- 上一个 change 实证：数据集曾在重建中被静默替换（1924–1983 → 1950–2026），无任何闸门报警；本机 `db/tar-shards/` 仅存 1950–2026 共 78 个年份目录，`reference/ziwei-samples-toolkit` 不在盘上。
- 用户已拍板：基准范围正式采纳 **1950–2026**（B 方向）；两项上游受阻项记 defer。
- 既有可复用面：`build-fixtures.ts` 的写盘前分歧自检（重建闸门）；`ziwei.duckdb`（836M）仍在盘上，`build-duckdb --mode=dataset` 可从它重导 parquet（重导成本远低于全量重建）；quality-gates 计数纪律（「基准回归的分层与登记」上一次修订刚清掉同类写死计数）。

## Goals / Non-Goals

**Goals:**

- 数据集获得「导出时自报、日常对账」的指纹守卫，静默替换从结构上不可能再发生。
- 基准范围追认为 1950–2026，fixtures 重建流程恢复可用，全部计数陈述与实况对齐。
- 普查获得基线对拍形态，文墨表变化可跨次审阅。

**Non-Goals:**

- 不补 1924–1949（本地分片不存在，上游网络拉取不在本次范围；将来补年同样是显式动作）。
- 不做文墨表提取器重跑、真太阳时语料扩充（上游工具仓不在盘上——deferred，见 D4）。
- 不动亮度对拍口径、不扩日常样本量、不触内核。

## 不可逾越的约束

- fixtures 重建 MUST 通过 `build-fixtures` 写盘前分歧自检；diff 审阅后才能提交。
- 日常回归零原生依赖前提不破：指纹对账只读文件字节。
- 生成文件纪律：`build-duckdb` / `build-fixtures` 都是生成器——改的是生成器与登记面，重导产物，禁止手改产物。
- `kernel-contract` 冻结面、`compare.ts` 契约零协同改动。

## Decisions

### D1 指纹形态：文件字节 sha256 + 自报登记面，前置验证可复现性

- **决策**：登记面落 `db/dataset/MANIFEST.json`（数据集自描述、与数据集同进退入库），内容 = 两个 parquet 的字节 sha256 + 总条数 + 年份范围 + 生成日期 + 血统备注。对账断言住 `repo.test.ts`（层 6——它守的是仓库内数据资产完整性，纯文件字节，不属排盘对标语义），`LAYERS` 的 suites 同步登记一行。
- **前置验证（任务 1.1）**：从现有 `ziwei.duckdb` 重导一次数据集，与盘上 parquet 比哈希——若一致，字节哈希成立且**顺带实证重导可复现**；若不一致（parquet 写出含随机因子），回落**逻辑指纹**（条数 + 年份范围 + 主键序列哈希，需 DuckDB，对账挪到中档入口），此备选留档。血统备注按实况诚实填写：「原始导出血统未记录（2026-11-21 前的静默重建）；2026-11-21 重导实证与现行内核 3,000 条比对零差异」。
- **备选否决**：指纹放 `fixtures/manifest.json`——否决，理由是登记面应与数据集同处、由数据集的生成器自报；放 fixtures 就是手抄第二份，副本必漂移。对账放层 1——否决，它不比对盘面语义，层 1 的比对器语境不属它；层 6 的「仓库自洽」主题契合。
- **后果两面**：收益 = 静默替换结构性消灭、血统有页可翻、日常回归零新依赖（+读 12.8 MiB 算哈希约 0.3s）；代价 = 将来每次合法重导都须走生成器自报（人工直接换文件会红——这正是目的）。
- **deletion test**：删掉指纹对账 = 数据链回到「换文件无人知」；删掉登记面 = 对账无锚点恒红或恒真，两者都是能力损失而非复杂度搬家。

### D2 基准范围正式化：追认 1950–2026，重建走既有闸门

- **决策**：`build-fixtures` 抽样年份改 1950–2026（77 年 × 5 条 = 385，槽位轮转公式的覆盖性质对任意年数成立）；重导 fixtures 走分歧自检——**自检本身就是血统实证闸门**：若新数据集与现行内核不符，红并逼审，静默固化不可能。`chart.test` 的「300 条（60 年 × 5 条）」硬计数改为从 manifest 派生（yearRange 与 count 自报互证）——这是计数纪律的补课，与上次「14 个测试文件」同型。文案同步：README（命令注释 / 分工表 / 文件清单 / 「fixtures 从哪来」节）、AGENTS（npm test 行）、`full-corpus` 范围标签改为**运行时自报**（描述性文案不再手写第二份）、`verify-source` 的指引注明 reference/ 缺失时的状态。
- **备选否决**：保持 300 条（77 年非均匀抽）——否决，抽样设计的可解释性（每年 5 条、轮转铺满）比凑整数重要；扩到每年 5 条以上——否决，覆盖扩张归中档 / 全量档，日常档守「秒级」定位。
- **后果两面**：收益 = 重建流程复活、全部陈述与实况一致、基准血统页补齐；代价 = 日常层 1 样本 300 → 385（层 1 耗时约 +28%，整体 npm test 约 +0.4s）、基准快照换血需一次 diff 审阅。
- **文件物理位置无变动**——不涉三类字符串排查。

### D3 普查基线：固定单点入库基线 + 显式两形态

- **决策**：普查工具加两形态——存基线（把当前分布表写成 `test/fixtures/brightness-census-baseline.json`）与对基线（逐行 diff：新增 / 消失 / 计数变化的组合逐条点名，零变化输出一行确认）。**不加路径参数**——审计基线就该有固定归属，参数化是不必要自由度（deletion test：删掉参数化不损能力）；基线文件属审计参照，明确不进任何闸门面。
- **后果两面**：收益 = 文墨表修订 / 换版的变化范围可跨次审阅、注错演练可回归验证；代价 = 文墨表合法修订后须显式重存基线（一次命令，红绿不存在——它不是闸门）。

### D4 Deferred 两项的登记方式

文墨表提取器重跑、真太阳时 / 晚子时语料扩充，记入 design 本节与 proposal（不进 tasks）：受阻原因 = 上游工具仓 `reference/ziwei-samples-toolkit` 不在本机（private、无 LICENSE，历史上以 reference/ 形态存在）；恢复条件 = 上游仓重新可用（用户提供路径或重新放置）。届时亮度逐格验证与语料扩充各为一个独立小 change，不回填本变更。

### 抽象三问自检

不新增抽象：指纹 = 生成器一处自报 + 层 6 一条断言；基线 = 普查工具的两个形态参数；无新模块、无新接口。接缝判据：每个交付物 = 一个文件内的小增量 + 一行登记（suites / manifest 节）。

## Risks / Trade-offs

- [parquet 重导不确定（哈希不一致）] → 任务 1.1 前置验证；回落逻辑指纹（备选路径已在 D1 留档），对账挪中档入口
- [重导 fixtures 时分歧自检红] → 这正是血统闸门在工作：停下来查清新数据集引擎血统，按「升级 iztro 的流程」处置，不得往白名单加条目了事
- [385 条新基准引入未知差异] → 分歧自检逐条对拍现行内核，diff 审阅留痕；重叠年（1950–1983）已有 3,000 条中档零差异的先行证据
- [AGENTS / README 清点遗漏] → tasks 用「grep 全部旧计数串」作为完成判据，不靠记忆
- [指纹断言误伤（正常重导未登记）] → 生成器自报使「合法重导」与「登记」原子完成；错误信息写明两条出路（重导 or 显式重登记）

## 实现期重大发现：数据链独立性已断（超出本变更范围，如实留档）

任务 2.3 文案清扫时发现：`tools/db/tar-source.ts` 的 v4 物化管线**直接 import 本仓
`scripts/algorithm.ts` 的 `generateChart`** 做「v4 现场排盘补 chart」——即现行
db/dataset（1950–2026）的 chart 就是**本仓内核自己的输出**。证据链：

- 亮度普查在新 fixtures（385 条）上分歧 **0** 处（旧 1924–1983 数据集对文墨表分歧 19.3%）
- 重导三方哈希一致 = 数据集 ≡ ziwei.duckdb 重导，而 duckdb 由 v4 管线排盘灌入

**效力影响**：fixtures/数据集对本仓内核而言是「冻结的自快照」——
① 回归锁定价值**保留**（内核未来改动必红）；② 「外部基准」「iztro 2.5.8 独立来源」
叙事**失效**（KNOWN_DIVERGENCES 的「样本陈旧、本项目对」类差异不可能再出现）；
③ 亮度普查对独立参照的审计价值失效，但**监测文墨表未来漂移的价值保留**
（fixtures 亮度是被冻结的旧内核快照，改表即现分歧——3.2 演练实证）。
④ README / AGENTS 的「外部基准比对」表述与本发现冲突，属后续 change 处置面。

## Migration Plan


顺序依赖：指纹登记先行（1.1–1.3）→ 范围正式化（2.1–2.3，含 fixtures 重导）→ 普查基线（3.1–3.2）→ 集成验收（4.x）。回滚 = revert 单个 commit；fixtures 重导前旧 fixtures 在 git 历史中随时可回。
