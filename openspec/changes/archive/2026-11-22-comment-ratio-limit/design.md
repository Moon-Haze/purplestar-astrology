# Design

## Context

见 proposal.md 的 Why。`code-style` 既有「长注释外置 docs」requirement 的 10 行阈值与本变更的 30% 占比是两条独立纪律：前者管连续块长度，后者管整文件密度，互不替代。

## Goals / Non-Goals

**Goals**: 建立全仓统一、无豁免的注释占比上限；固化可复现的度量口径；为存量超标文件给出明确的"随改动收敛"处置。

**Non-Goals**: 不在本变更内批量删改注释；不修改刚生效的四层注释规范；不改代码行为。

## 不可逾越的约束

- 阈值 30 为 spec 单一登记值，度量脚本从 spec 读取，不写死。
- 不设豁免清单：任何"这个文件例外"的条目都是对规范的破坏。
- 生成物边界来自 `AGENTS.md`「项目约束（不可动）」，不是本规范新增的豁免。

## Decisions

### D1：分母取非空行，注释行含 `*` 续行

- **收益**：与仓库现有 `long-comment-check.ts` 的行分类口径一致，度量可复用；空行不参与比例，避免用空行稀释。
- **代价**：`/** */` 密集的纯类型文件天然高比例（实测 11 个纯类型文件平均 53.6%），收敛时需外置 `@remarks` 正文而非删类型约束。
- **否决备选（按字符数计）**：中英文混排下字符数波动大，不如行数直观可核验。

### D2：存量不设豁免、随改动收敛

- **收益**：一个标准，无旁路；与用户拍板一致。
- **代价**：89/159 文件当前超标，规范生效初期即"大面积红"，须靠后续实施批次逐步消化；度量报告须如实列报，不做状态伪装。
- **否决备选（豁免清单）**：用户明确否决。

### D3：规范与实施分离

- **收益**：本变更只动规范面，不引发大规模注释删改；实施批次独立走变更流程，保真可逐批验收。
- **代价**：规范生效与全仓达标之间存在时间差，期间不得声称全仓合规。

## 三问核验

- deletion test：删掉这条 requirement，注释膨胀无纪律约束，复杂度不会转移，是真实缺失。
- 接缝判据：无新扩展点，不适用。
- 抽象 justify：阈值单一登记 + 度量脚本读取，删除后脚本需写死数值，故有存在价值。

## Risks / Trade-offs

- [规范生效即大面积红] → 如实列报，不伪装达标；实施批次按热区优先收敛。
- [收敛时误删类型约束注释] → 优先外置 `@remarks` 正文到 `docs/code/`，保留字段级防错说明；外置需经 humanizer-zh 润色并守引文纪律。
- [度量脚本口径分歧] → 脚本从 spec 读阈值，输出行级明细，两次运行一致。

## Migration Plan

本变更：写 spec delta + 三处规范同步（spec / AGENTS / config）。后续：另立实施变更按目录分批把超标文件降至 ≤ 30%，每批跑保真校验（代码 token 零变更）与三件套。
