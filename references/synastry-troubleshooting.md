# 排障：合盘（synastry）报错对照表

本文件是 `SKILL.md` 的延伸——**遇到报错或异常输出时才读**，正常解读流程用不到。

合盘是本 CLI 的 `synastry` 命令（2026-09-30 三 skill 合一时并入）：它自己**不排盘**，只消费两份 `astrology --json` 的产物。出生信息类报错（未收录城市、缺性别等）发生在 `astrology` 那一步，报错也由那边给，见 [troubleshooting.md](troubleshooting.md)。本文件管三类错：**输入与命盘 JSON 不合格**（占绝大多数）、**参数用错**、**启动期失败**。以下报错文案均为实测原文（2026-10-01，路径 / 数值随现场变）。

## 输入与命盘 JSON 不合格（最常见）

这类报错的根因通常不在 `synastry` 本身，而在排盘那一步用错了形态或文件没落好。见到就先回去复核排盘命令。

| 报错（实测原文，截取）                                                                                     | 成因与处理                                                                                                                                                                                                                             |
| ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `缺少 --charts：本命令不排盘，两方命盘都得由排盘命令的 --json 产出。`                                       | 两份盘一个都没给。照报错里自带的两步走：① 先各排一张（**`--json` 不带 `--palaces`**）：`node scripts/purple-star.ts astrology --date … --city … --gender … --json > /tmp/a.json`；② 再 `node scripts/purple-star.ts synastry --charts /tmp/a.json,/tmp/b.json`（甲先乙后）。 |
| `--charts 应给两个文件路径（甲,乙，逗号分隔），实得 1 个：only-one.json`                                     | `--charts` 只收**恰好两个**逗号分隔的路径。同一文件给两次是合法用法（自盘对照）。                                                                                                                                                        |
| `读不到甲方命盘文件：/tmp/不存在.json`（下一行 `ENOENT: no such file or directory …`）                       | 路径写错，或排盘那步根本没跑成（重定向建了空文件 / 文件在别的机器上）。报错会附上重排指路；先用 `ls` 确认两份文件都在且**非空**。                                                                                                       |
| `甲方命盘文件不是合法 JSON：/etc/passwd`（下一行 `Unexpected token 'r', "root:x:0:0"… is not valid JSON`）   | 重定向拿到的东西不是 JSON。**最常见**：排盘命令失败了，写进文件的是那行错误信息——打开文件看一眼就知道。                                                                                                                                 |
| `甲方命盘文件里没有命盘对象（顶层键 \`chart\`）：<路径>`（附「顶层实际有」清单）                             | **拿 `astrology --palaces --json` 顶替了标准 `--json`**。`--palaces` 形态**顶层就是命盘**（`birthInfo / lunarInfo / … / palaces / …`），没有 `chart` 键，也没有合盘需要的四化落宫与排盘依据。改用不带 `--palaces` 的 `astrology --json` 重出。 |
| `乙方命盘文件缺 \`nativeSiHua.located\`（生年四化落宫）：<路径>`                                             | 那份 JSON 被裁剪过或出自旧版形态。「四化入夫妻宫」一节依赖它，缺了会静默少一节结论，故此处拦下。用 `astrology --json` 重新生成。                                                                                                        |
| `乙方命盘文件缺 \`lateZi\`（晚子时标记）：<路径>`                                                            | 同上。晚子时口径会让该方整张盘改变，缺了标记就无法提示用户复核。                                                                                                                                                                        |
| `乙方命盘文件缺 \`basis\`（排盘依据）：<路径>`                                                               | 同上。真太阳时校正与出生地解析的说明由排盘方给出，`synastry` 不重算——缺了它，合盘输出会丢掉「这张盘是怎么来的」那段提示。                                                                                                               |
| `命盘里找不到「夫妻宫」宫 —— 这份 JSON 是 purplestar-astrology 排的吗？`（附该盘实际十二宫名清单）            | 那份 JSON 的宫名口径不对（不是本项目排的盘，或宫名被改过）。按报错列出的实际十二宫判断来源；确认来源无误就重排。                                                                                                                         |
| `命盘异常：乙方命宫（地支 卯）不在十二宫内 —— 这份 JSON 已损坏`                                              | 命盘对象损坏（命宫地支在 `palaces` 里找不到对应宫）。重新排一张。                                                                                                                                                                       |

## 输出里的警告（不是报错）

| 输出（实测原文）                                                                                                                                                             | 含义与处理                                                                                                                                                                                     |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `⚠️ 甲方出生时间落在 23:00–23:59（晚子时），这份盘按当日早子时口径排。`（下一行指引回排盘命令重排该方，重跑合盘）                                                             | 任一方 JSON 的 `lateZi.candidate` 为真且未按晚子时排时出现。**合盘前先向用户确认钟点**；确需晚子时口径，回 `astrology` 加 `--late-zi` 重排该方，再重跑 `synastry`——否则合盘结论建立在一方口径存疑的盘上。 |

## 参数报错

| 报错（实测原文）                                       | 成因与处理                                                                                                                                                                                                                             |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `未知参数 --cahrt。运行 help 查看全部参数。`            | 旗标拼错。⚠️ 实测**没有**「最接近的是 --xxx」提示——`--chart` 这个参数已不存在（现在叫 `--charts`，且编辑距离超出建议阈值）。运行 `node scripts/purple-star.ts help` 查看参数面。                                                         |
| `未知参数 --a-chart。运行 help 查看全部参数。`          | a- / b- 前缀**已退役**（2026-09-30 起 `--charts` 单参数收两盘），不再有「前缀只有 synastry 命令认」的专门报错。两份路径写进同一个 `--charts` 值。                                                                                       |
| `synastry --date 1990-01-01` → 仍报「缺少 --charts…」   | **出生信息参数被静默收下不用**：本 CLI 的参数作用域是 skill 级全量，`--date` / `--time` / `--gender` / `--city` / `--config` 等在解析层不拒收（与旧独立 skill 版「当场报 未知参数 --date」**不同**），但 `synastry` 一个都不读，最终仍按缺 `--charts` 报错。别被「参数没报错」骗了——合盘永远从两份 `--json` 文件走。 |

## `astrology --json` 的顶层键契约（synastry 读什么）

标准形态（`astrology --json`，不带 `--palaces`）顶层固定 10 键（实测）：

```
chart / patterns / mingGongSummary / nativeSiHua / liuNianSiHua / liuYueSiHua / liuNianPalace / xiaoXian / lateZi / basis
```

`synastry` 只读其中 4 个：`chart`（十二宫 + 出生信息）、`nativeSiHua.located`（生年四化落宫）、`lateZi`（晚子时标记）、`basis`（排盘依据）；`patterns` / `mingGongSummary` / `liuNian*` / `xiaoXian` 属于排盘解读侧，合盘一个字不读。逐项校验的实现住在 `scripts/synastry/chart-view.ts` 的 `readAnalyzeJson()`（按「甲」「乙」逐项点名）。

## 启动期报错

依赖没装或 Node 版本过低时，引导层用统一格式拦下所有命令（实测原文，路径与版本随环境变）：

```
[ziwei 启动失败] 无法加载 @/ziwei/algorithm
  Cannot find package 'iztro' imported from <skill根>/scripts/ziwei/algorithm.ts
  当前内核根：<skill根>/scripts（来源：技能自带内核）
  → Cannot find module 'iztro' / 'lunar-typescript'：依赖未装。
     在 skill 根（<skill根>）执行 npm install 即可（依赖清单见该目录 package.json）
  → registerHooks is not a function 或 TS 语法报错：Node 版本过低，需 ≥ 22.15（当前 v26.10.0）
```

两个分支各挡一种成因：`iztro` / `lunar-typescript` 找不到 → 依赖未装，在本目录（仓库根即 skill 根）`npm install`；`registerHooks is not a function` 或 TS 语法报错 → Node 版本过低，需 ≥ 22.15（本 CLI 靠 Node 原生类型擦除直接加载 `.ts`，不注册解析钩子）。

## 确认跑的是哪一份内核

只有一份——内核按脚本自身位置（`import.meta.url`）定位，不依赖 cwd，也没有环境变量可覆盖。`node scripts/purple-star.ts selftest` 输出的**第二行**（形如 `内核根：<路径>`，来源标注「技能自带内核」）就是当前生效的那一份，交付解读前据此核对。

```bash
node scripts/purple-star.ts selftest   # 回归自检（排盘 / 古籍 / 合盘三段，末行自报项数；实测 120/120）
npm test                               # 仓库级回归：cli / 排盘不变量 / 三合派约束 / 引文核对（test/citations.test.ts）都在这条里
```
